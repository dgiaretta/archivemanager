Preserving digital information: the three OAIS techniques

Keeping the bits safe isn't enough. Software, hardware and what people know all change, so information has to stay independently understandable to its Designated Community — the people who must be able to use it — in the ways its Preservation Objectives set out. OAIS (CCSDS 650.0-M-3) names three fundamental ways of achieving that. Each is described below, with how to do it in this application. Editing needs the edit password.

1. Add Representation Information

Keep the Data Object exactly as it is, and add the Representation Information needed to understand it: its structure (how the bits make numbers, text, records and arrays), its semantics (what each value means, in what units), and other Representation Information such as the software that reads it. Representation Information needs its own Representation Information in turn, until what's left is something the Designated Community already understands. This is the technique to use first: nothing about the data changes, so nothing can be lost.

  • In RepInfo Tools, describe a binary or self-describing format as a tree of fields, records and choices, give each element its meaning (name, definition, units, code list, scale and offset, fill value, valid range), and test the generated DFDL, Kaitai Struct and DRB descriptions against a sample file. Saving to the archive adds Structure Representation Information (one or several equivalent descriptions, any one of which will do) and Semantic Representation Information for every element, attached to a Data Object.
  • For a format that is already defined and read by existing software (a spreadsheet, delimited text), describe only what each column means; it's saved with a format profile and the software that reads it.
  • Add anything else — a specification document, a dictionary, other software — with the Entities editor, linked to the Data Object's Representation Information.
  • Check that it is enough: a Data Object whose bits have a storage location can be opened from its page through its Representation Information alone, as a table, spectrum or image in TOPCAT, SPLAT, DS9 or Aladin (see below).

2. Transformation

When adding Representation Information isn't enough, or a format is becoming obsolete, rewrite the Data Object in another format. This changes the Content Information, so it has to be checked and recorded: decide which values must survive (its Transformation Information Properties), check them after the Transformation, and add Provenance Information saying what was done. The result is an AIP Version, a candidate to replace the original. A Transformation that can't be shown to be reversible is a Non-Reversible Transformation, where those checks are the evidence that nothing that matters was lost.

  • Open the Data Object's page and choose Transform…. It needs a storage location for its bits and a DFDL, DRB SDF or Kaitai Struct description to decode them.
  • Choose the new format: any format with a DFDL description in the archive. Describe a new one in RepInfo Tools first if needed.
  • Say what makes each element of the new format: repeated once per occurrence of an element of the old format, copied (with an optional scale and offset, e.g. degrees to radians), counted, or a constant. A first guess matches elements by name and meaning; the mapping can also be edited as text.
  • Choose the Transformation Information Properties to check, with a tolerance if the values may change slightly (e.g. stored with less precision).
  • Try it: the new data is written with the new format's description, decoded again with that same description, and each property's values are compared with the original's. You see whether each was preserved, whether the Transformation is reversible, and can download the new file. Nothing is saved.
  • Transform: the new file is kept in the archive, and recorded as a new Data Object in an AIP Version (linked to the original AIP), with Fixity Information (its SHA-256 digest) and Provenance Information recording the Transformation — what it started from, the mapping it followed, when, and each check. The original is left as it is.

3. Hand over complete AIPs to another archive

If this archive can no longer look after some information, another archive can take responsibility for it. That only works if each Archival Information Package is complete: its Content Information (the Data Object with all the Representation Information needed to understand it) and its Preservation Description Information (Provenance, Context, Reference, Fixity and Access Rights Information), so the receiving archive can carry on without asking anything.

  • Build the AIP with the Entities editor, as described in section 5: attach the Content Information and each kind of Preservation Description Information, the Designated Community and Preservation Objectives, and any Transformation Information Properties. Transformations create their AIP Versions this way automatically.
  • Check that it is complete by looking at it: an AIP's page lists everything linked to it, the graph shows the whole package and what it points to, and the SPARQL console can find packages missing a part.
  • What can be handed over today: each Data Object's Representation Information manifest (Turtle naming its bits and every description, from its page) and its bits from their storage location; the OAIS ontology and its local extensions, from the home page. An archive running this application can load Turtle with /entities/import.
  • Not yet: there is no one-step export of a whole AIP — its description, all its Representation Information and its bits — as a single package for another archive. Until there is, handing over an AIP means gathering those parts as above.

1. Browse, no login needed

Catalogue and Accession Register are public search/browse views. From any record, Records, Agents, Provenance events, and Mandates link to each other (an agent's page lists what it created, and so on).

2. See a record's OAIS mapping

Records management and digital preservation ask different questions about the same material. RiC-O (Records in Contexts) describes who created something, in what context, and how to find it again — the concerns of archival description. OAIS asks what has to be kept alongside the bits for that material to still make sense decades from now: its Content Information, its Preservation Description Information, and (see section 5 below) who it has to remain understandable to and by what tests. The two vocabularies' classes don't line up one-to-one, so rather than forcing a false equivalence, this app's bridging ontology connects them two ways: a class-level correspondence using SKOS closeMatch/broadMatch/ relatedMatch (deliberately weaker than owl:equivalentClass where the concepts genuinely don't coincide), and, where a specific record actually has OAIS preservation structure built for it, an individual-level bridge:hasOAISCounterpart link to that structure.

Open any record and follow its "OAIS mapping" link to see both halves in action. The top half shows which OAIS classes correspond to the record's RiC-O type(s), read live from the bridging ontology; the bottom half, if the record has one, shows the actual linked OAIS preservation-description structure (Information Object → Data Object → Bit, and so on).

3. Explore the interactive graph

Graph shows the whole archive as a network; "View in graph" on any record/agent/activity/mandate page shows a focused view around just that one instead, with an adjustable depth (1–4 hops) from the toolbar above the graph. Statistics links to the full graph too, as a visual complement to its own aggregate counts. Every listing page — Entities, Agents, Records, Provenance events, Mandates, Accession Register, Catalogue search/explore, and the SPARQL console's own results — also has a "View this page as a graph" button: it graphs exactly the items currently on screen (one page of results, not the whole list), starting at depth 1, so a long list stays as quick to graph as a single record. On the SPARQL console specifically, this graphs every distinct resource any column of the results actually refers to, regardless of which variable name your query bound it to; it's only offered when at least one result cell is a real resource rather than a literal.

  • Colour shows which ontology a node belongs to (blue = RiC-O, brown = OAIS, grey = other, per the legend above the graph); a dashed red edge is a cross-ontology link made via the bridging ontology, not a property either vocabulary defines on its own.
  • Mouse and keyboard: scroll to zoom, drag the background to pan, drag a node to reposition it, double-click a node to open its detail page in the same tab.
  • Right-click a node for a menu instead of the browser's own: "Open detail page" (opens in a new tab, so you don't lose your place in the graph), plus a "Links" section listing every external URL-valued property that node has — e.g. an rdfs:seeAlso — by property name, each also opening in a new tab. This is also how you retrieve the actual bits, not just metadata: a Data Object, Digital Object, or its RiC-O Instantiation may carry a im:hasStorageLocation link to where the file itself lives (e.g. a Dropbox or cloud storage URL); right-click that node and choose it to download or open the file directly. A Data Object whose Representation Information says how to read and view its data also gets "View the data": "View with TOPCAT" for a table, and "View with SPLAT" when its table is all numbers (a spectrum); "View with DS9" and "View with Aladin" for an image, plus "Download as FITS" for Fiji/ImageJ, which doesn't use SAMP. Each "View with" sends the data to that application running on your computer (over SAMP; it asks you to allow the page). The menu also has its Representation Information manifest. How the data's kind is decided is below. If you don't have them, download TOPCAT (topcat-full.jar) or SPLAT-VO (splat-vo-<version>.jar; see About SPLAT), and run either with java -jar; for images, SAOImage DS9, Aladin Desktop or Fiji. Right-clicking empty background leaves the browser's normal menu alone. The menu closes on Escape, on a click elsewhere, or as soon as you drag or zoom.
  • Highlighting — the checkboxes above the graph, grouped into entity types, node properties, and relationship types — dims everything that doesn't match what's checked; combining checkboxes from more than one group narrows further rather than widening (e.g. an entity type plus a relationship type shows only edges of that type touching a node of that type). They're built from whatever's actually present in the currently-loaded graph, not a fixed list, so what you see checked always matches what's on screen. "Clear highlight" resets all three groups at once.
  • A very large neighbourhood (or the full archive) may be truncated to stay responsive — a banner says so when it happens. Switch to a focused view for the full graph, or a smaller depth for a focused view that's still too big.

4. Query it directly

SPARQL console runs arbitrary SELECT queries against the union of the data and ontology graphs — useful for answering a question none of the built-in pages happen to show, or for exploring the ontologies themselves.

5. Log in to create or edit anything

Everything above is read-only and needs no account. Log in with the shared edit password to unlock:

  • Entities — the generic editor. Create an individual of any RiC-O or OAIS class, then add its types, literal properties, and relationships one at a time. /entities/import (linked from that page) bulk-loads a pasted Turtle document instead.

    This is also how a complete Archival Information Package gets built: starting from a Data Object or Information Object, attach its Content Information and Preservation Description Information (Provenance, Context, Reference, Fixity, and Access Rights Information, each in turn) — and, just as required, who it has to remain understandable to and by what tests. Attach a Designated Community (the audience the object must stay independently understandable to), which can be linked to the Preservation Objective(s) it's tested against, and any Transformation Information Property whose value needs checking after a Non-Reversible Transformation such as a format migration. None of these three are defined by the Designated Community itself, though — an Agent (normally the archive doing the preserving) defines them, consulting the Designated Community and other stakeholders as appropriate. Adding any of these relationships offers a "+ Create new …" option in the target picker, so the component it points to doesn't need to exist beforehand — it's created and linked in the same step.

  • Bulk Upload Spreadsheet (linked from the Catalogue page) — import a CSV/XLSX of NAM-format records in one go.
  • RepInfo Tools — a guided editor for building Kaitai Struct, DFDL, and/or DRB descriptions of a binary or self-describing data format (built-in FITS, telemetry, CSV and HDF5 starting points). A byte layout is edited as a tree of fields, records (including CSV-style delimited-text records) and choices; any element can be optional under a condition or repeated a computed number of times, using small expressions such as sample_pairs * 2 or packet_type = 2 that refer to fields read earlier. Beyond the structure, give any element its semantics — a semantic name, definition, units (with a vocabulary link), a code list, a scale factor and offset, a fill value and a valid range — and saving turns those into real Semantic Representation Information: one individual per element, nested like the description (name as its rdfs:label, definition as its skos:definition, units linked via im:hasUnitOfMeasurement, code lists as SKOS concept schemes), gathered under one overall Semantic Representation Information alongside the Structure Representation Information for whichever generated description(s) you keep. Sample tests show each value's meaning (a code's meaning or the scaled value with units), which branch each choice took, and any bytes the description doesn't cover. For a byte layout, the DRB outputs are an installable drb-python driver package and a DRB SDF schema for GAEL's Java DRB, and you can test the Kaitai Struct and DFDL descriptions, the DRB SDF schema and the drb-python driver against a sample data file before saving (the drb-python test needs Python with pip install drb on the server; the others need nothing extra — the Kaitai Struct compiler is bundled). You can also choose which languages to generate: choosing fewer than all four unlocks what only they can describe, such as bit fields, records of a stated size, nil values, quoted CSV and number formats (DFDL), or elements at an absolute offset and zlib-compressed records (Kaitai Struct). For anything the editor can't express — checksums, encryption, other compression, records spread over several lines — write the Kaitai Struct, DFDL or DRB description by hand, from scratch or by extending the generated one; the page has worked examples, and the hand-written text is used for the sample test, download and save (it's checked first so it can only describe data). The drb-python driver package also has add-ons giving a decoded file's semantics, metadata and checks (values outside their valid range or code list), and can carry a Python add-in written by hand — code the driver calls to decrypt or decompress a file, or to check a CRC. Being code, an add-in is only run in sample tests if the server is set up to allow it. Each description can also write back: decode a sample and write it again with the same description, to check that the result is byte-for-byte identical (the description is then enough to re-create the file), or to write a copy with some values changed (/header/count = 3) and download it. For a spreadsheet or delimited text (.xlsx, .xls, .ods, .csv), whose format is already defined and which software already reads, describe only what each column means — the columns can be taken from a sample file and tested against one. That's saved with a format profile (the format's registry identifier, refined with its version and, for text, its character encoding and delimiter) and the software that reads it (e.g. Excel or any application that reads OOXML spreadsheets, any one of which will do), or with Representation Information already in the archive. To look at the data in TOPCAT, SPLAT or an image viewer, download a bundle from the preview page: a Representation Information manifest naming your data file and each description explicitly, with a generated table view and, for an image, an image view (see below for when each is made). A Data Object in the archive whose bits have a storage location can be opened straight from its page: its manifest by URL, its data as a VOTable or, for an image, as FITS, or sent to TOPCAT, SPLAT, DS9 or Aladin on your computer with "View with …".
  • Transform a Data Object into another format, the second of OAIS's three ways of preserving digital information: "Transform…" on its page. Choose a format with a DFDL description in the archive, say what makes each of its elements (repeated once per occurrence of an element of the old format, copied with an optional scale and offset, counted, or a constant — a first guess matches names), and choose the Transformation Information Properties to check. "Try it" writes the new data, decodes it again with its own description and checks each property's values; nothing is saved. "Transform" keeps the new data in the archive and records it as a new Data Object in an AIP Version, with Fixity Information and Provenance Information recording the Transformation: what it started from, the mapping it followed, and its checks.

Table, spectrum or image: which viewers are offered

RepInfo Tools doesn't ask what kind of data you have: it works it out from the shape of the byte layout you describe, and saves the answer as view specifications (im:ViewSpecification, with im:viewKind "table" or "image") in the data's Semantic Representation Information. The archive then reads those back to decide what to offer.

  • Table — the rows are the first record directly in the root that repeats (a stated number of times or to the end of the file), e.g. one reading or star per row; with no such record, the whole file is one row. The columns are that record's fields that occur once and hold a number or text (raw bytes and repeated fields are left out), each with its units and meaning. If there are no such fields, no table view is made. A table is offered to TOPCAT, and served as VOTable.
  • Spectrum — not a separate view: a table is treated as a spectrum when its table view has at least two columns and every column is a number (e.g. wavelength, flux, error). It's then offered to SPLAT as well as TOPCAT. One text column (a station name, say) means TOPCAT only.
  • Image — a record directly in the root that repeats (a row) and holds exactly one repeated field of numbers (its pixels, in order), e.g. a row repeated height times, each holding a pixel repeated width times. Any other fields in the row record are ignored for the image. The pixel field's units and meaning become the image's. An image is offered to DS9 and Aladin, and served as FITS (also for Fiji/ImageJ), with the units in BUNIT and the meaning and origin in the header's comments. Rows are kept in the order the data holds them: the first row is FITS row 1, which these viewers show at the bottom.

One description can be both: when the image's row record is the first repeated record and has fields of its own besides its pixels, it gets a table view of those fields and an image view of the pixels. And every viewer needs a DFDL or DRB SDF description, which the server decodes the data with, and a storage location for the Data Object's bits. Since the views are ordinary view specifications, a manifest or Representation Information written by hand can give its own, of either kind, instead. Decoding builds every pixel as an element, so very large images are slow: a 128 × 128 image takes a few seconds.

Data description languages

Notes on each of the data description languages RepInfo Tools works with — how a format is described, how this application runs the descriptions, what each engine reports (typed values, byte positions), and its known limitations:

  • DFDL — the Open Grid Forum's Data Format Description Language, run by Apache Daffodil.
  • Kaitai Struct — .ksy descriptions compiled ahead of time into parser code.
  • DRB — GAEL's Java Data Request Broker and its SDF schemas.
