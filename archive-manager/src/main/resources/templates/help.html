What this application is

This is a prototype archive. It takes in information and records — accession in records-management terms, ingest in OAIS terms — and brings together two disciplines that usually live in separate systems:

  • Records management, using Records in Contexts (RiC-O, the International Council on Archives' ontology). It describes the records: what they are, who created them, in what activities and under what mandates, and how they relate to each other, so they can be found and understood as evidence.
  • Digital preservation, using OAIS (the Open Archival Information System reference model, ISO 14721 / CCSDS 650.0-M-3). It preserves the information, so that it stays usable and understandable as software, hardware and knowledge change, using OAIS's three fundamental preservation techniques: adding Representation Information, Transformation, and handing complete packages to another archive.

A bridging ontology links the two, so a record described with RiC-O can point to the OAIS package that preserves it, and the other way round. Both are held as linked data (RDF) in one store, so everything can be browsed, graphed and queried together.

This page follows the life of the information: first how to take it in, describe it, create its Representation Information, see how it relates, and check that each Archival Information Package has every component OAIS requires; then the three preservation techniques; then how to view and analyse the data.

Why astronomical applications? To show that preserved data can actually be used, this prototype opens it in astronomical tools: TOPCAT and SPLAT for tables and spectra, DS9 and Aladin for images. They were chosen because they are designed to fetch data from remote archives, then analyse, compare and combine information from many different sources (they talk to each other, and to archives, using Virtual Observatory standards such as VOTable and SAMP). That is exactly what the data in an archive needs. Nothing depends on them, though: the archive serves the data in standard formats, described by its Representation Information, so other applications could be used in their place.

Working with the archive

Browsing — no login needed

Everything can be looked at without an account. Catalogue and Accession Register are public search and browse views. From any record, Records, Agents, Provenance events and Mandates link to each other (an agent's page lists what it created, and so on), and Entities lists everything, of any kind.

Logging in to take in or change anything

Taking information in, editing, creating Representation Information and preserving all need the shared edit password: log in. Browsing, viewing and downloading stay open to everyone.

Taking information in (accession and ingest)

  • Records, in bulk: the Bulk Upload Spreadsheet (linked from the Catalogue page) imports a CSV or XLSX of records in NAM's format in one go, creating each record, its creator and identifiers, and an OAIS package (Content Information and Preservation Description Information) for each record linked to it; the upload as a whole is recorded as one accession in the Accession Register.
  • Any linked data: /entities/import (linked from Entities) loads a pasted Turtle (RDF) document — records, OAIS packages, anything — checking it fully before anything is added.
  • One item at a time: Entities creates an individual of any RiC-O or OAIS class; Records creates records.
  • Data and its description: RepInfo Tools saves a data format's description to the archive together with a Data Object for the data (see below).
  • The bits: the archive keeps descriptions, not data files. A Data Object points to where its bits are kept with im:hasStorageLocation — a Dropbox or cloud storage link, say — which the archive fetches from when it needs to read the data. Bits the archive makes itself, such as the result of a Transformation, are kept in its own store.

Describing records, and editing properties and relationships

Records are described with RiC-O: a Record, Record Part or Record Set, its title and description, who created it (an Agent), the activities it came from, the mandates that govern it, its identifiers and dates, and the records it is part of.

Any individual's page has Edit, which opens the generic editor: add or remove its types, its properties (text, numbers, dates, links) and its relationships to other individuals, one at a time, choosing from the properties RiC-O and OAIS define for it. Adding a relationship offers "+ Create new …" in the target picker, so what it points to doesn't need to exist beforehand — it's created and linked in the same step.

Creating Representation Information

Representation Information is what's needed to understand a Data Object's bits: their structure (how the bits make numbers, text, records and arrays), their semantics (what each value means, in what units), and other Representation Information such as the software that reads them.

  • Binary and self-describing formats: RepInfo Tools is a guided editor for building Kaitai Struct, DFDL and DRB descriptions of a data format (with FITS, telemetry, CSV and HDF5 starting points). A byte layout is edited as a tree of fields, records (including CSV-style delimited-text records) and choices; any element can be optional under a condition or repeated a computed number of times, using small expressions such as sample_pairs * 2 or packet_type = 2 that refer to fields read earlier. Give any element its semantics — a semantic name, definition, units (with a vocabulary link), a code list, a scale factor and offset, a fill value and a valid range. Test each generated description against a sample file before saving: sample tests show each value's meaning (a code's meaning or the scaled value with units), which branch each choice took, and any bytes the description doesn't cover. Each description can also write back a sample, to check the result is byte-for-byte identical (the description is then enough to re-create the file) or to write a copy with some values changed.
  • Choosing languages: generating all of them limits the description to what every language can express; choosing fewer unlocks what only they can describe, such as bit fields, records of a stated size, nil values, quoted CSV and number formats (DFDL), or elements at an absolute offset and zlib-compressed records (Kaitai Struct). For anything the editor can't express — checksums, encryption, other compression — write the description by hand, from scratch or by extending the generated one. For a byte layout the DRB outputs are an installable drb-python driver package and a DRB SDF schema for GAEL's Java DRB; the driver can carry add-ons (semantics, metadata, checks) and a hand-written Python add-in (run in sample tests only if the server allows it).
  • Formats software already reads (.xlsx, .xls, .ods, .csv): describe only what each column means — the columns can be taken from a sample file. That's saved with a format profile (the format's registry identifier, refined with its version and, for text, its character encoding and delimiter) and the software that reads it.
  • Saving adds it to the archive as real Representation Information, attached to a Data Object: Structure Representation Information (several equivalent descriptions, any one of which will do), and one Semantic Representation Information for every element, nested like the description, with its name, definition, units and code list. Anything else — a specification document, a dictionary, other software — can be added with the editor.
  • Writing it out: before saving, the preview page downloads each description (.ksy, .dfdl.xsd, .drb.xsd, the drb-python package). After saving, Download the data description on the Data Object's page, or any Representation Information's, gives it all as a zip: description.ttl in RDF, and each description and view specification as a file of its own.

Viewing relationships

Records and their OAIS packages. RiC-O and OAIS ask different questions about the same material: RiC-O who created something, in what context, and how to find it again; OAIS what has to be kept alongside the bits for it to still make sense decades from now. Their classes don't line up one-to-one, so the bridging ontology connects them two ways: class-level correspondences using SKOS closeMatch/broadMatch/relatedMatch (deliberately weaker than owl:equivalentClass where the concepts don't coincide), and individual-level bridge:hasOAISCounterpart links from a record to the OAIS structure that preserves it. Open any record and follow its "OAIS mapping" link to see both: which OAIS classes correspond to its RiC-O type(s), and its actual linked OAIS structure.

The graph. Graph shows the whole archive as a network; "View in graph" on any page shows a focused view around that one item, with an adjustable depth (1–4 hops). Every listing page, and the SPARQL console's results, also has "View this page as a graph", which graphs exactly the items on screen.

  • Colour shows which ontology a node belongs to (blue = RiC-O, brown = OAIS, grey = other); a dashed red edge is a link made through the bridging ontology.
  • Mouse: scroll to zoom, drag the background to pan, drag a node to move it, double-click a node to open its page.
  • Right-click a node for "Open detail page" (in a new tab), its links — including im:hasStorageLocation, to download the bits themselves — and, for a Data Object whose Representation Information says how to view it, "View the data" (see below).
  • Highlighting: the checkboxes above the graph (entity types, node properties, relationship types) dim everything that doesn't match; combining groups narrows further.
  • A very large neighbourhood may be truncated to stay responsive — a banner says so; use a focused view or a smaller depth.

Querying. The SPARQL console runs any SELECT query over the data and the ontologies together — for questions no page answers, such as which packages lack Fixity Information.

The components of an OAIS Archival Information Package

An Archival Information Package (AIP) is what OAIS preserves: everything needed for its information to stay understandable, kept together. By the OAIS Information Model, an AIP has:

  • Content Information (exactly one): the Content Data Object, its bits, and the Representation Information needed to interpret them;
  • Preservation Description Information (exactly one), with Reference (identifiers), Provenance (its history), Context (how it relates to its environment and other information), Fixity (checks that it hasn't changed) and Access Rights Information (who may use it, and how);
  • Packaging Information (exactly one): how the components are bound together and how to extract them;
  • a Package Description (at least one): for finding the package.

Build an AIP with the editor: create an Archival Information Package and add these relationships in turn, creating each component as you go. As OAIS requires, also say who the information must remain understandable to and by what tests: a Designated Community, linked to the Preservation Objective(s) it's tested against, and any Transformation Information Properties whose values must survive a Transformation. These are defined by an Agent (normally the archive), consulting the Designated Community, not by the Community itself.

Checking it. An AIP's page shows a checklist of every required component: present, missing, or (for Packaging Information) provided when the AIP is written out as a BagIt bag. Add what's missing with the editor. The page also lists everything linked to the AIP, and "View in graph" shows the whole package.

An AIP stored as a package. Often the components aren't described in the archive itself but are inside the package the AIP is stored as — for instance an AIP made by Eternal, kept as a .7z or .zip file and named by the AIP's storage location. Then the AIP's page offers Map its package to the AIP components: the archive fetches the package, opens it, checks its BagIt bag (every file's checksum, and Payload-Oxum), and shows, for each component, where in the package it is and what it says there — the upload spreadsheet carried in it (metadata.csv, read with the column definitions in metadata_definition.xml), the METS file's PREMIS (each file's format with its PRONOM identifier, its checksum, and events such as ingestion and virus checks), the checksum audit and the Preservation Description Information file — and which components the package doesn't have. The table can be downloaded as CSV.

Preserving digital information: the three OAIS techniques

Keeping the bits safe isn't enough. Software, hardware and what people know all change, so information has to stay independently understandable to its Designated Community — the people who must be able to use it — in the ways its Preservation Objectives set out. OAIS names three fundamental ways of achieving that. Each is described below, with how to do it in this application.

1. Add Representation Information

Keep the Data Object exactly as it is, and add the Representation Information needed to understand it. Representation Information needs its own Representation Information in turn, until what's left is something the Designated Community already understands. This is the technique to use first: nothing about the data changes, so nothing can be lost.

  • Create it as described in Creating Representation Information: describe the format's structure and the meaning of every element in RepInfo Tools, and add any other Representation Information with the editor.
  • Check that it is enough: a Data Object whose bits have a storage location can be opened from its page through its Representation Information alone, as a table, spectrum or image (see Viewing and analysing the data). If that works, the description is enough for software to read the data.
  • Keep it independent of this application: Download the data description writes it out in standard forms (RDF, DFDL, Kaitai Struct, DRB).

2. Transformation

When adding Representation Information isn't enough, or a format is becoming obsolete, rewrite the Data Object in another format. This changes the Content Information, so it has to be checked and recorded: decide which values must survive (its Transformation Information Properties), check them after the Transformation, and add Provenance Information saying what was done. The result is an AIP Version, a candidate to replace the original. A Transformation that can't be shown to be reversible is a Non-Reversible Transformation, where those checks are the evidence that nothing that matters was lost.

  • Open the Data Object's page and choose Transform…. It needs a storage location for its bits and a DFDL, DRB SDF or Kaitai Struct description to decode them.
  • By mapping, in the archive: choose the new format — any format with a DFDL description in the archive (describe a new one in RepInfo Tools first if needed) — and say what makes each of its elements: repeated once per occurrence of an element of the old format, copied (with an optional scale and offset, e.g. degrees to radians), counted, or a constant. A first guess matches elements by name and meaning; the mapping can also be edited as text. Choose the Transformation Information Properties to check, with a tolerance if the values may change slightly (e.g. stored with less precision).
    • Try it: the new data is written with the new format's description, decoded again with that same description, and each property's values are compared with the original's. You see whether each was preserved, whether the Transformation is reversible, and can download the new file. Nothing is saved.
    • Transform: the new file is kept in the archive and recorded as a new Data Object in an AIP Version (linked to the original AIP), with Fixity Information (its SHA-256 digest) and Provenance Information recording the Transformation — what it started from, the mapping it followed, when, and each check.
  • With another application: if a converter, script or other program does the Transformation, use "Or transform it with another application" on the same page. Download the data and its data description, transform it there, then upload the result and fill in what was done: the application and its version, who did it and when, the steps or settings, what the result is interpreted using, whether it is reversible, and how each Transformation Information Property fared. Where you say which element of the new format a property's values went to, and the archive can decode both the old and new data, it checks them itself; otherwise it records what you report. The person and the application are recorded in its Provenance Information.
  • Either way, the original AIP's Reference, Context and Access Rights Information are carried over to the AIP Version as copies (the Reference Information also naming the new Data Object), and a new Package Description says what it is and how it was made — so the AIP Version has every component an AIP needs whenever the original did. The original is left as it is.

3. Hand over complete AIPs to another archive

If this archive can no longer look after some information, another archive can take responsibility for it. That only works if each AIP is complete — every component listed in The components of an OAIS Archival Information Package — so the receiving archive can carry on without asking anything.

  • Make sure it is complete: the AIP's page shows which components are present and which are missing; add what's missing with the editor, as described in Working with the archive. For an AIP already packaged elsewhere (e.g. by Eternal), "Map its package to the AIP components" shows whether its package holds every component, and checks its bag.
  • Hand it over: on the AIP's page, Download as BagIt writes it out as a BagIt bag (RFC 8493, zipped), the packaging format archives and libraries use to move content between them. data/aip.ttl describes the AIP and everything it's made of in RDF with the OAIS Information Model's terms; data/objects/ holds its Data Objects' bits, data/descriptions/ each description as a file, and data/ontologies/ the ontologies that define the terms. SHA-256 manifests let the receiving archive check, with any BagIt tool, that every file arrived complete and unchanged.
  • For large data, or bits already kept where the receiving archive can fetch them, BagIt, referring to the bits leaves the bits out of the bag and lists them in fetch.txt, BagIt's way of referring to files: the URL to fetch each from and where it goes in the bag. The manifest still has each file's checksum, so the bag is complete, and checks out, once they're fetched.
  • The bag names every component of the AIP in oais-aip-components.txt — whether each is present, which individuals in aip.ttl are it, and which files hold it — and bag-info.txt says whether the AIP is complete and what's missing. The bag itself is the Packaging Information, so an AIP without its own gets one describing the bag.
  • An archive running this application can load the AIP's description with /entities/import.

Viewing and analysing the data

A Data Object whose bits have a storage location, and whose Representation Information says how to read them, can be opened from its page or its right-click menu in the graph:

  • Its Representation Information manifest (Turtle), naming the data and each description explicitly: TOPCAT (with the oais-structure-topcat reader, format OAIS-RepInfo) and SPLAT open it by its address.
  • Its data as VOTable (a table or spectrum) or FITS (an image), decoded on the server through its Representation Information — standard formats that many applications read.
  • "View with TOPCAT", "SPLAT", "DS9" or "Aladin" sends the data to that application running on your computer, over SAMP (the page asks you to allow it). Fiji/ImageJ doesn't use SAMP: open the FITS file in it, or give it the FITS link's address.
  • "Launch TOPCAT" or "Launch SPLAT", for those who'd rather not download, start and connect the applications themselves: it starts the application with the data already loaded, downloaded from the archive. It needs OpenWebStart, a free launcher installed once (the successor to Java Web Start, which current Java no longer has): the link downloads a .jnlp file, which OpenWebStart opens. The application is signed with the archive's own self-signed certificate: the first time, OpenWebStart shows the publisher and asks whether to trust it — choose to always trust it, and later launches go straight through. It's offered when the archive has been given the application to serve.
  • "See the image here", for an image: the archive's own viewer, in the page, with nothing to install. Choose the contrast stretch (linear, square root, logarithmic, asinh), the display limits, the colours and the zoom; drag to pan, use the mouse wheel to zoom, and point at a pixel to see its value and units.

As explained at the start, these astronomical applications are used because they are made to fetch data from remote archives and to analyse, compare and combine information from many sources; any application that reads VOTable or FITS could be used instead. If you don't have them: TOPCAT (topcat-full.jar) or SPLAT-VO (splat-vo-<version>.jar; see About SPLAT), each run with java -jar; for images, SAOImage DS9, Aladin Desktop or Fiji. RepInfo Tools' preview page also downloads a bundle for a local data file: a manifest naming your file and each description, with a generated table view and, for an image, an image view.

Table, spectrum or image: which viewers are offered

RepInfo Tools doesn't ask what kind of data you have: it works it out from the shape of the byte layout you describe, and saves the answer as view specifications (im:ViewSpecification, with im:viewKind "table" or "image") in the data's Semantic Representation Information. The archive reads those back to decide what to offer.

  • Table — the rows are the first record directly in the root that repeats (a stated number of times or to the end of the file), e.g. one reading or star per row; with no such record, the whole file is one row. The columns are that record's fields that occur once and hold a number or text, each with its units and meaning. A table is offered to TOPCAT, and served as VOTable.
  • Spectrum — a table whose view has at least two columns, all numbers (e.g. wavelength, flux, error), is also offered to SPLAT. One text column means TOPCAT only.
  • Image — a record directly in the root that repeats (a row) and holds exactly one repeated field of numbers (its pixels, in order). The pixel field's units and meaning become the image's. An image is offered to DS9 and Aladin, and served as FITS, with the units in BUNIT and the meaning and origin in the header. Rows are kept in the order the data holds them: the first row is FITS row 1, which these viewers show at the bottom.

One description can be both a table and an image. Every viewer needs a DFDL or DRB SDF description, which the server decodes the data with, and a storage location for the bits. Since views are ordinary view specifications, Representation Information written by hand can give its own. Decoding builds every pixel as an element, so very large images are slow: a 128 × 128 image takes a few seconds.

Data description languages

Notes on each of the data description languages RepInfo Tools works with — how a format is described, how this application runs the descriptions, what each engine reports (typed values, byte positions), and its known limitations:

  • DFDL — the Open Grid Forum's Data Format Description Language, run by Apache Daffodil.
  • Kaitai Struct — .ksy descriptions compiled ahead of time into parser code.
  • DRB — GAEL's Java Data Request Broker and its SDF schemas.
